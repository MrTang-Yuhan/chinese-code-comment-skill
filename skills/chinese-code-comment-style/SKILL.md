# 中文代码注释规范化

## 目标和边界

在不改变注释事实和代码行为的前提下，统一注释的语言语法、声明位置、文档标签、格式、术语和项目约定，使编译器、文档生成器、lint 和初次阅读代码的人都能正确理解。

- 处理行注释、块注释、docstring、JSDoc、Javadoc、Doxygen、Go doc、Rust doc 和 C# XML 文档等目标语言惯用形式。
- 对照项目 formatter、linter、文档生成配置和语言版本；没有项目约定时使用目标语言官方惯例。
- 可调整注释的换行、缩进、标签顺序、标点、标题层级和紧邻位置，但不得凭空增加事实或改变原有语义。
- 不负责把英文翻译成中文、不负责补齐缺失的 why 注释、不修改函数实现、变量名、字符串、日志、错误文本或公共 API。
- 跳过生成文件、依赖目录、压缩文件和二进制文件，除非用户明确指定。

## 工作流程

1. **先检查 Context7 MCP**：查看当前 Codex 会话是否有可用的 Context7。若注释规范依赖第三方框架、文档工具或版本敏感的 API，优先查询匹配版本的官方文档；不可用时使用仓库配置、现有注释和工具输出。
2. **识别规范来源**：读取目标语言版本、formatter/linter 配置、文档生成配置和附近代码的既有风格；记录哪些约定是项目要求，哪些只是语言默认。
3. **核对注释语法和位置**：确认注释类型在目标语言中合法，并紧邻被解释的类型、成员、函数参数或控制流块；不能让注释被解释为代码、字符串或错误的声明。
4. **核对文档契约**：逐一检查 `@param`、`@return`、`@throws`、`Args:`、`Raises:`、`<param>`、`# Arguments` 等标签与实际签名一致；每个类属性和结构体变量的注释必须能唯一对应声明。
5. **统一格式**：按项目约定整理缩进、换行、列表、标题、标点、术语大小写和标签顺序；保留代码围栏、链接、占位符和 API 标识符。
6. **验证**：运行可用的 formatter、lint、文档生成、编译或测试；至少运行 `git diff --check`，确认差异只改变注释表示和文档标记，不改变代码语义。

## 常见规范检查

- Python：类和函数优先使用合法 docstring；`Args:`、`Returns:`、`Raises:` 参数名与签名一致，装饰器注释位于装饰器堆叠的正确位置。
- JavaScript/TypeScript：JSDoc 标签合法且紧邻声明；`@template`、`@param`、`@returns` 和可选参数标记与类型签名一致。
- Java/C#：Javadoc 或 XML 标签闭合、参数名一致，废弃 API 使用项目约定的标记；注解本身不被误写成 Python 式运行时包装说明。
- Go：导出声明的 Go doc 以声明名称开头；`//`、`/* */` 和示例代码符合 gofmt/go vet 能识别的形式。
- C/C++/Rust：Doxygen 或 Rust doc 使用合法的 `///`/`/** */`/`//!`；模板参数、生命周期、所有权和宏说明放在对应声明附近。
- 所有语言：每个分支和可达路径的注释位置清晰，嵌套块、`break`、`continue`、提前返回、异常和清理路径不能被外层一条注释混淆。

## 调用示例

```text
请使用 chinese-code-comment-style，整理 src/api.ts 的 JSDoc，使 @param/@returns 与实际签名一致，统一换行、标签顺序和注释位置；不要翻译或增加新的说明，不改业务代码。
```

```text
请使用 chinese-code-comment-style，按照项目的 clang-format、Doxygen 和 C++ 版本规范检查 src/queue.cpp，修正注释语法、缩进、成员对应关系和控制流注释位置。
```

## 完成前自检

- 所有注释都使用目标语言合法语法，并紧邻其被解释的声明或代码块。
- 文档标签、参数名、返回值和异常说明与真实签名一致；每个成员/结构体变量都有唯一对应注释。
- 注释的换行、缩进、标点、术语、标题和标签顺序符合项目配置或语言惯例。
- 没有翻译、补写事实、修改代码逻辑、改变字符串或破坏链接/代码示例。
- 已运行可用的格式化、lint、文档生成、编译或测试，并记录验证结果。
