# 中文代码注释增强

## 目标与边界

把现有代码解释成初学者能够顺着阅读的中文，同时保持代码行为、公开接口、数据格式和错误处理不变。注释必须忠实于实际实现；无法从代码、测试、调用方或项目资料确认的行为，要明确标注“需要业务确认”，不要把猜测写成事实。

只在用户要求添加、完善或审查代码注释时使用本 skill。除非用户另行授权，不要顺手重构、修复业务逻辑、改变公共 API、改写错误文本、调整日志或修改生成文件。

仓库地址：<https://github.com/MrTang-Yuhan/chinese-code-comment-skill>

## 支持语言

本 skill 支持以下语言：C、C++、Python（包括 PyTorch 张量代码）、JavaScript、TypeScript、Java、Go、Rust、C#。处理混合语言目录时，按每个文件的语言版本、注释语法、文档工具和项目约定分别建立覆盖清单；不能把一种语言的装饰器、注解或文档标签语义套用到另一种语言。

## Why 优先

每条有信息量的注释都应优先回答 **为什么存在、为什么这样写、违反它会怎样**，再补充必要的“做什么”和“怎么做”。不要把代码逐字翻译成中文：

```text
不合格：遍历用户列表。
合格：按输入顺序遍历用户列表，保证返回结果与调用方提交的编号顺序一致；如果改成无序集合，分页结果会不稳定。
```

较长的注释按以下顺序组织：

1. **目的**：这段代码解决什么问题，为什么需要它。
2. **约束和原因**：为什么选择当前算法、数据结构、语法、顺序或失败策略；依赖哪些不变量。
3. **影响**：成功、失败、并发、资源、性能或后续流程会发生什么。

对复杂或罕见语法必须说明“机制 + 选择原因 + 不这样写的后果”。例如，不能只写“使用 `std::move`”，还要说明它为什么能转移资源、调用后源对象处于什么可用状态，以及不用它可能产生哪次复制。

## 不可省略的覆盖规则

处理用户指定的文件或代码范围时，建立覆盖清单并逐项完成：

1. **类型声明**：类、接口、结构体、联合体、枚举、trait、protocol、record、模块等定义处必须有中文注释，说明职责、适用场景、重要不变量、生命周期和为什么采用这种抽象。
2. **成员和字段**：类的每个成员属性、属性访问器背后的存储字段、C/C++ 的 `struct`/`class`/`union` 每个成员（包括位域、匿名嵌套成员、指针、引用、`const`/`static` 成员）、其他语言结构体的每个变量、全局状态和重要常量都必须逐一有紧邻的中文注释。说明用途、为什么需要该字段、单位、默认值、可空性、所有权、线程安全要求、取值范围或与其他字段的关系。即使多个成员类型相同、名称自解释或连续声明，也不能省略或合并；一条注释必须能明确对应一个成员声明。
3. **函数定义和参数**：每个成员函数、普通函数、构造器/初始化器、析构器、重载/override、闭包、lambda 或对外暴露的回调，在定义处必须有中文文档注释。除了功能、返回值、异常或错误、可见副作用外，必须**逐一解释每个形参**：参数名、用途、为什么需要、类型/单位/有效范围、默认值或可选性、可空性、是否会被修改、所有权/生命周期/线程约束，以及与其他参数的关系。`self`/`this`/`cls` 等隐式接收者在影响所有权、状态或继承行为时也要说明；`*args`、`**kwargs`、可变参数、命名参数和模板/泛型参数不能只写“原样转发”，要解释其允许的形状和保留调用契约的原因。构造器参数还必须说明如何映射到成员、是否复制/移动、校验失败如何处理。
4. **复杂语法**：模板和泛型、指针与引用、借用和生命周期、宏、装饰器、注解/属性、反射、闭包、高阶函数、迭代器、正则表达式、位运算、智能指针、异步语法、查询表达式、递归、短路表达式、类型断言、模式匹配、`defer`、`unsafe` 等，必须在语法块前或首次关键用法处解释机制、选择它的原因，以及不用它可能造成的影响。
5. **代码块和每条路径**：每个 `if`、`else if`、`else`、`for`、`while`、`do`、`switch/case/default`、`match` 分支、`try/catch/finally`、`with`、`defer`、协程、并发选择、列表推导或其他可独立理解的控制流块，都要在块开始前或块内第一条语句前用中文说明：为什么进入该块、保持什么不变量、失败/成功如何影响后续流程。每个分支体都必须单独解释，不能让外层注释代替内层路径说明；同一块中的正常完成、条件不满足、循环零次执行、循环结束、`break`、`continue`、提前 `return`、抛出异常和 `catch/finally` 收尾等可达路径，也要在对应路径附近分别说明后续影响。条件表达式、模式守卫和短路表达式产生的不同路径同样适用。

对没有花括号的单行分支，也要把注释放在语句上一行。注释可以使用行注释、块注释、文档注释或语言惯用的 docstring，但必须使用目标语言合法的注释语法，并紧邻被解释的声明或代码块。

### 参数注释专项规则

参数说明必须能从函数定义处直接定位，不能只在调用方、函数体内部或单独的 README 中解释。推荐按声明顺序逐项列出，并回答以下问题：

- **用途与 why**：这个参数代表什么，为什么由调用方传入，而不是从成员、全局状态或默认值推导。
- **边界**：类型、单位、有效范围、默认值、空值/缺省语义、空集合与空字符串的区别，以及非法值如何处理。
- **数据流**：参数来自哪里、是否会被修改、是否跨异步/线程边界、是否借用/拥有/移动资源，返回值或异常如何受它影响。
- **参数关系**：参数之间是否必须成对出现、顺序是否有意义、某个开关是否改变另一个参数的解释。

如果函数只接收一个 `options`/`config`/请求对象或解构参数，也不能把它当成一个无法展开的“参数对象”：对会影响行为的每个属性逐项说明名称、默认/缺省语义和 why；同时说明对象本身是复制、借用还是由调用方继续持有。

各语言优先使用本语言的参数文档格式：Python docstring 的 `Args:`/`Raises:`、JSDoc 的 `@param`、JavaDoc 的 `@param`、C++ Doxygen 的 `@param`、Go doc 的逐项参数段落、Rust doc 的 `# Arguments`/`# Errors`、C# XML 的 `<param name="...">`。参数名必须与实际签名一致；如果语言没有标准标签，就在定义紧邻的中文注释中逐行列出。不要把多个参数合并成“参数若干”或只解释最复杂的一个。

### 装饰器、注解和属性的专项规则

扫描目标范围内所有装饰器样式的语法，包括 Python/JavaScript/TypeScript 的 `@...`、Java/Kotlin 的 `@Annotation`、C# 的 `[Attribute]`、Rust 的 `#[...]`/`#![...]`，以及承担类似职责的宏、框架路由声明和编译器属性。每个装饰器或装饰器堆叠都要在装饰器上方或首次使用处写中文 why 注释，至少说明：

- **何时执行**：是在模块导入/类或函数定义时执行，还是每次调用、编译、宏展开、框架扫描或反射时生效；不要让读者误以为所有装饰器都在运行时包装函数。
- **改变什么**：是否替换目标函数/类、改变参数或返回值、注册路由、添加元数据、改变可见性/序列化，或仅影响编译器检查。
- **为什么使用**：它消除了哪类重复代码、统一了哪条策略，或者满足了什么框架契约；不用它会增加什么复制、遗漏、性能或可维护性风险。
- **副作用和顺序**：是否有缓存、重试、鉴权、日志、注册表写入等副作用；多个装饰器说明应用顺序及顺序变化的影响。Python 中上方装饰器最后应用，`@outer`/`@inner` 等价于 `target = outer(inner(target))`。
- **元数据与调试**：包装器是否保留原函数名称、文档字符串、签名和异常堆栈；Python 包装器通常应解释 `functools.wraps` 的 why，其他语言则说明反射/文档工具能否看到原始声明。

不要只写“这是装饰器”或“这是注解”。Python 的 `@property`、`@staticmethod`、`@classmethod`、参数化装饰器、类装饰器和框架路由都要说明它们改变访问方式或注册时机的原因；Java/Kotlin 注解和 C# Attribute 通常保存元数据，由编译器、框架或反射读取，并不等同于 Python 的运行时函数包装；TS/JS 装饰器还要注明编译目标和运行时提案语义。

### PyTorch 张量维度注释专项规则

处理 PyTorch 张量代码时，追踪张量在函数中的形状，并在每个张量操作处标明输入、必要的中间形状和输出形状。所有改变张量维数或各维大小的操作都要注释，包括 `nn.Linear`/卷积/Embedding、`reshape`/`view`/`flatten`、`permute`/`transpose`、`matmul`/`bmm`/`einsum`、拼接/堆叠、索引、池化、插值、归约、`squeeze`/`unsqueeze`、padding 和广播等；即使某次操作的输入输出尺寸碰巧相同，也要标出该操作的维度关系，换序操作按变换后的维序书写。`softmax`、dropout、激活、归一化和 residual add 等形状保持不变的张量操作也要写出输入到输出的形状，并标注“形状不变”；有广播时则写清各输入形状、广播方向和结果形状，不能误称为形状不变。

形状注释优先放在代码行尾；若会超过项目 formatter/linter 的行宽或显著影响可读性，则放到对应语句上一行。单条表达式包含多个连续张量操作时，用一条注释按执行顺序串联每个可确认的中间形状，避免漏掉链中某一步：

```python
# [B, L, D] -> [B, L, 3D] -> [B, L, 3, D] -> [3, B, L, D]
qkv = self.qkv(x).reshape(B, L, 3, D).permute(2, 0, 1, 3)

weights = self.dropout(torch.softmax(scores, dim=-1))  # [B, K, L, L] -> [B, K, L, L]（形状不变）
context = weights @ value  # [B, K, L, L] @ [B, K, L, D_head] -> [B, K, L, D_head]
x = x + context  # [B, K, L, D_head] + [B, K, L, D_head] -> [B, K, L, D_head]（形状不变）
```

若一个函数/方法处理张量，在函数体开头集中声明本函数注释中使用的符号；保留 docstring 为函数首个语句时，把符号注释块放在 docstring 之后、第一条可执行语句之前。只声明实际用到的符号，但跨函数、跨文件复用相同含义，不能为了局部方便换名或换义：

```python
def forward(self, x):
    # B: 批大小，L: 序列长度，D: 特征维度，K: 注意力头数，D_head: 每个注意力头的特征维度
    ...
```

默认符号约定：`B` 表示 batch size，`L` 表示序列长度，`D` 表示特征维度，`V` 表示词表大小，`C` 表示通道数，`H`/`W` 表示空间高/宽，`K` 表示注意力头数。符号一经采用，整次处理都保持同义；例如当模型维度和每头维度需要区分时，使用 `D_model` 和 `D_head`，不要让 `D` 在不同位置分别表示二者。`H` 固定表示空间高度，patch 网格行/列数用 `H_patch`/`W_patch`、patch 总数用 `N_patch` 等不冲突的下标符号；不要把 `H` 改作 patch 数。对于输入/输出维度、空间尺寸或其他确需区分的量，使用一致的下标形式（如 `D_in`/`D_out`、`H_out`/`W_out`），并在函数符号注释块中声明其含义。

形状和符号必须从实际代码、调用方、模型配置及已锁定版本的 PyTorch 契约中推导，不能只根据变量名猜测；遇到动态尺寸时保留有依据的符号或公式，不得编造具体数值。如果某个形状或广播关系仍无法确认，标注“需要业务确认”，不要给出貌似精确的形状。添加这些说明只改注释，不拆分或改写张量表达式。

## 工作流程

1. **先检查 Context7 MCP**：开始处理前先查看当前 Codex 会话实际暴露的 MCP 工具或服务器，确认是否有可用的 Context7。不要假定 Context7 一定存在，也不要为了满足本步骤临时安装或启用外部服务。
2. **优先核对相关文档**：如果 Context7 可用，且目标代码涉及第三方库、框架、语言特性或版本相关行为，先用 Context7 解析准确的库/包标识并查询与项目版本匹配的官方或权威文档，再结合仓库证据写注释。Context7 用于核对通用机制和 API 契约，不能替代项目源码、锁定版本、测试或调用方对实际行为的证明。
3. **回退并记录限制**：如果 Context7 不可用、访问失败、找不到对应库或没有匹配版本，继续使用仓库源码、锁文件、已有文档、测试和其他可用工具完成任务，不要因此阻塞；对仍无法确认的语义按“需要业务确认”处理。
4. **确认范围和语言**：读取目标文件及附近调用代码，识别语言、版本、格式化工具和项目已有注释风格；跳过生成文件、依赖目录、压缩文件和二进制文件，除非用户明确要求处理。
5. **保留现有上下文**：检查已有注释是否仍然准确。保留有价值的说明，修正过时内容；不覆盖用户未完成的修改。
6. **建立覆盖清单**：逐项列出类型、每个字段/结构体成员、函数、每个参数、每个装饰器/注解/属性、罕见语法和控制流块，并把每个分支体、循环入口/零次跳过/正常结束/`break`/`continue`、早退和异常路径作为独立清单项。对 PyTorch 代码另列每个张量操作，记录其输入/输出维数与各维形状、形状保持不变的操作、广播和链式表达式中的中间形状，并核对函数符号声明及跨文件符号含义一致。对照函数签名核对参数名称和数量，扫描函数、类、异步函数、框架路由和装饰器堆叠，记录执行时机、应用顺序及是否改变签名或元数据。对于 C++ 结构体，字段清单必须一项对应一条注释，不能只检查 `struct` 上方是否有注释；成员清单也必须一项对应一个成员声明，不能按类型或连续声明合并核对。
7. **补声明级信息**：先注释类型、成员字段、全局变量和常量，让读者知道“这是什么”“为什么存在”和“保存什么”。
8. **补函数契约和参数清单**：在每个函数或方法定义处逐一列出所有参数，再说明输入、输出、失败路径和副作用；构造器要核对每个初始化参数与成员的映射、复制/移动和校验；长函数再按阶段解释数据流和设计原因。
9. **解释难点和控制流**：在复杂语法块前说明机制、选择原因和替代方案代价；为每个控制流块及其每条可达路径说明进入条件、处理目标、正常完成、跳过、早退、`break`/`continue`、异常和收尾路径的原因及后续影响。复核时逐项对照路径清单，不能用外层一条笼统注释覆盖嵌套分支。
10. **验证**：优先运行项目已有的格式化工具、静态检查、编译或测试，确认注释没有破坏字符串、缩进、宏、文档生成或语法。无法运行时，至少用 `git diff --check`、`git diff`、搜索和覆盖清单逐项复核；确认差异只涉及注释、文档字符串或用户明确授权的范围，不要凭肉眼假定业务行为未变。
11. **交付摘要**：总结修改的文件和注释层级，列出无法确认的假设，并报告执行过的验证命令及结果。

## 注释模板与质量标准

可使用以下模板，再按目标语言习惯改写：

```text
类型：为什么需要这个抽象；它维护什么不变量；谁负责创建和释放它。
字段：为什么要保存这个字段；单位/范围/默认值是什么；它与哪些字段或线程/所有权规则相关。
函数：为什么提供这个入口；逐一说明每个参数的用途、边界、来源、所有权和 why；返回/异常表示什么；有哪些副作用和失败恢复方式。
构造器：每个初始化参数如何映射到成员；是否复制/移动；缺省值和校验失败如何处理。
代码块：为什么进入该分支或循环；块内维护什么条件；为什么在这里 break/continue/return；之后会发生什么。
路径：每个分支、循环零次/多次执行、正常结束、跳过、提前返回、异常捕获和清理路径分别如何影响后续流程。
罕见语法：语法机制是什么；为什么选择它；不用它会增加哪种复制、竞态、泄漏、性能或可读性风险。
```

- 面向第一次阅读该模块的人，首次出现的专业词汇用一句话解释；保留 API、类型名、协议名等必要英文标识。
- 说明“为什么”和“影响”，不要机械重复变量名或语句本身。
- 准确描述空值、越界、重试、超时、异常、并发竞争、资源关闭和权限检查等边界条件。
- 注释简洁但完整；同一事实只在最靠近使用位置解释一次。局部变量只有在其含义、生命周期或不变量不明显时才额外注释，但用户明确要求的类型成员和结构体字段不能省略。
- 保持表达式求值顺序、控制流、公共 API、变量类型、日志内容和错误文本不变；只为注释需要而拆分声明时必须确认不会改变语义。
- 自动生成代码、第三方代码或格式化器会覆盖的文件，先说明范围，避免制造会立即丢失的注释。

## 语言注释习惯

使用目标语言最自然的文档形式：Python 优先使用类和函数 docstring，Java/JavaScript/TypeScript/C# 使用 Javadoc、JSDoc 或 XML 文档注释，Go 使用紧邻声明的 `//` 注释，C/C++/Rust 使用 `///` 或块文档注释。字段注释可以放在字段上方或同一行末尾，但每个字段必须能明确对应一条中文说明。

处理某种语言前，读取 [多语言详尽示例](references/multilingual-examples.md)，选择与目标语法最接近的样例。示例中的每种语言都同时展示类型/字段、函数契约、`if` 与循环或其他控制流、失败路径和不常见语法的 why 注释。

常见的罕见语法重点如下：

| 语言 | 需要解释机制、原因和后果的语法 |
| --- | --- |
| C/C++ | RAII、所有权、移动语义、模板/`concept`、`if constexpr`、`requires`、宏、位域、指针/引用、锁和协程 |
| Python | `@` 装饰器（包括参数化、堆叠、`@property`/`@classmethod`/`@staticmethod`）、生成器/`yield`、上下文管理器、推导式、`async/await`、动态属性和异常链 |
| JavaScript/TypeScript | 闭包、事件循环、`Promise`、可选链/空值合并、类型守卫、泛型和装饰器 |
| Java/C# | 泛型通配符、lambda/Stream/LINQ、注解、try-with-resources/`using`、异步、模式匹配和可空类型 |
| Go | goroutine、channel、`select`、`defer`、接口、嵌入、切片与数组、错误包装 |
| Rust | 所有权/借用/生命周期、trait bound、`?`、模式匹配、迭代器、`unsafe`、`Pin` 和 `async` |

特别注意不同语言的相似语法并不具有相同语义：Python 装饰器通常在定义期生成或替换对象，包装器在调用期执行；Java/Kotlin 注解和 C# Attribute 通常是声明元数据，实际行为由编译器、框架或反射代码读取；Rust 属性可能在编译期改变宏展开或 lint；TS/JS 装饰器的执行时机取决于编译器配置和采用的装饰器提案。注释必须说明目标项目的真实语义，不能把它们统称为“运行时装饰器”。

## 完成前自检

- 每个目标类型、每个类成员、每个 C/C++ 结构体/联合体成员和每个重要常量都有独立中文注释。
- 每个类属性、结构体变量和成员声明都能与唯一一条紧邻中文注释对应；没有因为字段同名、同类型、连续声明或“显而易见”而合并或省略。
- 每个函数、构造器、析构器、重载/override、闭包或回调的定义处都有函数契约注释，且每个参数（包括可变参数、命名参数、模板/泛型参数）都有可定位的逐项说明。
- 参数注释的名称和数量与实际签名逐一对应；每个构造器/初始化器参数都说明映射到哪个成员、默认/空值语义、校验、复制/移动或所有权影响。
- 每个装饰器、注解、Attribute、Rust 属性或宏式声明都说明了执行时机、应用顺序、改变的对象、why、副作用以及签名/元数据影响。
- 每个 `if/else`、`for/while/do`、`switch/case`、`match`、`try/catch`、`with`、`defer`、协程和并发选择块的每个分支和可达路径都解释了 why、约束和后续影响，包括循环零次执行、正常结束、`break`、`continue`、提前返回、异常和清理路径。
- 每个罕见语法块都解释机制、选择原因和不用它的后果。
- 对 PyTorch 张量代码，每个改变形状的操作、形状保持不变的操作、广播和链式中间形状都有准确注释；函数开头集中声明所用符号，且跨函数/文件的符号没有换义。
- 注释没有只复述代码，没有把猜测写成事实，也没有改变代码行为。
- 已运行可用的格式化、编译、静态检查或测试；无法运行的原因已在交付摘要中说明。
